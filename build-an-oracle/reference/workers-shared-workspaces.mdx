# Workers shared workspaces

Use this reference when integrating shared Topic work with Agentic Oracles on Cloudflare Workers. A workspace presents existing domain, project, Topic, Qi Flow, and file relationships. IXO services continue to own those records and their permissions.

This page documents `@ixo/oracle-runtime-workers`. The [tasks](/build-an-oracle/reference/bundled-plugins/tasks), [sandbox](/build-an-oracle/reference/bundled-plugins/sandbox), and [API endpoints](/build-an-oracle/reference/api-endpoints) pages describe the Node runtime; their Redis, NestJS, and deployment requirements do not describe Workers.

## Scope and activation

The supplied-evidence Topic drafting API is present in the runtime source baseline at commit `77012a8`. It is disabled by default. A deployed runtime must contain the API before its Portal integration is enabled. Source inspection and local tests do not establish live availability.

The approval, reconciliation, and credential-selection sections describe committed hardening through `e3ff01185d8c2ff53df2ce3f45b6faea6ec4b861`. The control-plane contracts, research API, fresh revocation checks, selected-credential scrubbing, and Composio restriction describe proposed PR implementation `94f8a191b6c4aa80bfc1aef9f7d23d9e5ee61cfe`. Research is inactive by default. These source revisions do not establish a published package, deployed service, or live acceptance result.

Shared research requires explicit host activation, an approved execution provider, and versioned file storage. Enabling the supplied-evidence drafting API does not enable research. Use a prepared candidate deployment for the [acceptance guide](/build-an-oracle/develop/verify-topic-research), and keep general user activation gated on that evidence.

| Foundation | Operator requirement |
| --- | --- |
| User execution | Deploy the Workers shell and `UserOracleDO`; each authenticated user has their own execution and database. |
| Collaboration | Configure IXO Matrix, the oracle gateway, and the intended Topic room audience. |
| Identity | Configure the oracle Decentralized Identifier (DID), key resolution, and signed User-controlled Authorization Network (UCAN) invocations. Research requires a reachable `UCAN_STORE_URL` for fresh revocation checks. |
| Durable owner storage | Use IXO Virtual Filesystem (VFS) owner storage. The example's `OWNER_STORE=matrix` is a local harness setting. |
| Skills and compute | Configure the existing skills registry and sandbox service; activate exact trusted skill pins and named credentials in host policy. |
| Model selection | Configure the runtime's operator-selected model provider and any supported user credentials. |
| Topic integration | Supply a host resolver for canonical Topic authority and the VFS resource. Verify the published recipe, its canonical digest, and its exact file-byte digest before activation. |

The shared workspace uses the IXO frontend action bridge: `action_call`, `action_call_result`, streaming, and authenticated realtime connections. The `agui` plugin name does not introduce a CopilotKit dependency. Neither CopilotKit nor CopilotKit Intelligence configuration is required.

Keep `ORACLE_DEBUG_ROUTES` disabled in shared deployments. If gateway debug routes are needed, configure `ORACLE_OPERATOR_DIDS` with the permitted operator DIDs. An absent allowlist leaves those enabled gateway routes available to any authenticated caller; a user-issued admin tool grant is consent, not operator authority.

## Authentication and authority

Workers protected requests use `Authorization: Bearer INVOCATION` and `X-Auth-Type: ucan`. The invocation is addressed to the oracle DID and uses the existing `*` capability on `ixo:oracle`. The validated signer selects the user's Durable Object. `x-did`, Topic IDs, and Matrix room IDs cannot select a different owner or confer publication rights.

`x-ucan-delegation` carries authorization for downstream calls. A delegation alone does not authenticate the Topic drafting API, including deployments that enable the shell's legacy bare-delegation fallback.

Keep these checks separate:

| Boundary | Authority |
| --- | --- |
| Room audience | Matrix membership and room confidentiality. |
| Agent action | The requester's current UCAN capabilities and host policy. |
| File access | Current VFS permissions for each file and version. |
| Topic publication | The canonical Topic repository's current authority, revision, and lifecycle checks. |
| Human review | The assigned reviewer acting under their own authenticated identity and current Topic rights. |

A room invitation grants no inherited execution authority. A reviewer does not read another user's model checkpoints, memory, or credentials. Shared views expose selected work status, sources, artifacts, and review records.

The shell authentication invocation is a short-lived reusable bearer. It is not bound to the HTTP method, path, or request body. Without `UCAN_STORE_URL`, successful validation can be cached until expiry. With the URL configured, shell authentication bypasses positive verdict reuse and checks revocation without a negative-result cache, failing closed on service errors. Concurrent verification is coalesced per token and authentication policy. DID key resolution retains its separate one-minute cache. Protect invocations accordingly; frozen inputs and canonical Topic checks provide additional operation boundaries.

Research requires `UCAN_STORE_URL` and a current delegation belonging to the requester. It rechecks expiry and revocation before execution and artifact mutations, and refuses research if current delegation validation or the revocation service fails. Matrix membership and an earlier successful Start cannot substitute for these checks.

## Supplied-evidence drafting API

Set `TOPIC_DELIVERABLES_ENABLED=true` on a runtime containing this API. When the setting is absent or different, the routes return `404`.

| Method | Endpoint | Behavior |
| --- | --- | --- |
| `PUT` | `/topic-deliverables/:operationId` | Start or recover the same bound operation. |
| `GET` | `/topic-deliverables/:operationId` | Read persisted status and output without starting a model turn. |
| `POST` | `/topic-deliverables/:operationId/cancel` | Persist cancellation, then abort the isolated task session. |

### Request shape

Start and cancellation require the same complete request body. Read has no body.

```json
{
  "topic": {
    "id": "TOPIC_ID",
    "roomId": "MATRIX_ROOM_ID",
    "threadId": "MATRIX_THREAD_ID",
    "attemptId": "ATTEMPT_ID"
  },
  "title": "Research brief",
  "goal": "Summarize the supplied evidence",
  "instructions": "Separate source evidence from assumptions",
  "sources": [
    { "label": "SOURCE_LABEL", "text": "SOURCE_TEXT" }
  ]
}
```

Unknown properties are rejected. `operationId` allows 1–128 ASCII letters, digits, hyphens, or underscores. The body limit is 128 KiB. At most 12 inline sources are accepted; each source text is limited to 32,000 characters. `title` allows 120 characters, `goal` 4,000, `instructions` 16,000, and IDs and source labels 255.

The runtime freezes the parsed body with schema-ordered object keys and unchanged array and string values. It performs no Unicode normalization. An identical Start after a lost response recovers the same task. A different body under the same operation ID returns `409`. Changed inputs require a new operation and attempt ID.

Cancellation can arrive before Start. The persisted cancelled operation fences a delayed identical Start; it cannot silently create work again. Cancellation after output completion returns `409`, including while Matrix delivery is pending.

### Response shape

Responses contain `operationId`, `taskId`, `topic`, `status`, and optional `runId`, `output`, and `delivery` fields. Completed output contains the full `markdown`, its lowercase hexadecimal SHA-256 in `sha256`, and `completedAt`.

| Field | Values |
| --- | --- |
| `status` | `queued`, `working`, `ready`, `stopping`, `cancelled`, `failed`, `interrupted`, or `paused` |
| `delivery` | `pending`, `delivered`, or `failed` |

`paused` describes a row paused outside this API; the API itself cannot pause it. Require `status === 'ready'` before offering an artifact for review. Failed Matrix delivery does not erase completed output or change `ready` to failed execution.

### Execution and recovery

The `supplied-context-markdown` profile runs once, with `approval: 'never'`, through the existing scheduler and durable run ledger. It binds no tools and rejects model-generated tool calls. It excludes personal preferences, memory, plugin hooks, page context, attachment processing, and capability routing. This path drafts from supplied text; it performs no live research.

One operation ID identifies one attempt. A restart recovers that attempt from its checkpoint. A terminal model failure, empty result, or unrecoverable interruption requires an explicitly created new operation. Delivery retries do not run the model again.

The API never accepts work, completes a Topic, or publishes a canonical outcome. Portal performs those mutations through its existing Topic repository after verifying current authority and the exact output.

### Errors

| Status | Meaning |
| --- | --- |
| `400` | Invalid operation ID or request body. |
| `401` | No valid signed invocation, including a delegation-only request. |
| `404` | API disabled, operation missing, or unsupported method. |
| `409` | Input conflicts with the bound operation, or cancellation arrived after output completion. |
| `413` | Request body exceeds 128 KiB. |
| `429` | New work exceeds the per-user task limit; an existing operation can still be recovered. |

## Artifact and review boundaries

Keep source snapshots and published results bound to immutable revisions and content digests. A mutable VFS file head is not the approved artifact. Artifact provenance identifies the requesting principal, operation, attempt, execution, and exact file version; it contains no credentials or bearer links.

A completed execution receipt records what ran and what it produced. A delivery record records what was shared. A reviewer decision records acceptance or requested changes against the exact artifact. Semantic evaluation, determination, external execution, and settlement remain separate records. Acceptance of a research brief does not prove that a real-world outcome occurred.

VFS uses managed encryption and current access controls. It is not end-to-end encrypted or zero-knowledge storage. Sandbox scratch state is replaceable compute state. Commit required work to durable storage before replacing a target; keep private checkpoints and memory outside the shared artifact projection.

## Revision-bound task approval

Workers `before-action` tasks persist an `approvalRequest` containing `id`, `digest`, `occurrence`, and delivery state. The digest binds the title, intent, schedule, approval mode, delivery room, execution profile, and scheduled occurrence. Updating the task invalidates the outstanding request and any approved occurrence.

The model's `resolve_task_approval` tool is inspect-only: it returns `reviewRequired` and cannot record a human decision. The model-facing `update_task` cannot remove an existing `before-action` gate. Record approval through a signed owner action:

| Method | Endpoint | Behavior |
| --- | --- | --- |
| `GET` | `/task-approvals/:taskId` | Read the owner's task and approval receipts. |
| `POST` | `/task-approvals/:taskId` | Approve or reject the exact outstanding request. |

```json
{
  "approvalRequestId": "CURRENT_APPROVAL_REQUEST_UUID",
  "decision": "approve",
  "note": "Optional audit note"
}
```

`decision` is `approve` or `reject`. `note` is optional and limited to 4,000 characters. Unknown properties are rejected; the request limit is 8 KiB. `taskId` must match `task_` followed by ASCII letters, digits, hyphens, or underscores. Both routes require a signed owner invocation; a delegation alone is insufficient.

Read returns `{ task, receipts }`. A decision response also includes `resolved`; a stale or mismatched pending request returns `409` with `resolved: false`. Receipts contain `taskId`, `actorDid`, `approvalRequestId`, `digest`, `occurrence`, `decision`, optional `note`, and `decidedAt`. The authenticated owner's DID is recorded by the host.

The scheduler refuses a missing, stale, or mismatched request ID or digest, and checks the binding again before execution. A later occurrence cannot inherit a prior occurrence's approval. Notes are audit records and never additional execution instructions. Revise the task inputs and obtain a new approval when the requested work changes.

Approval delivery is durable work. The runtime persists the request and arms its retry alarm before the first Matrix send. A restart retains the same request ID and delivery transaction identity; recovering delivery does not create another approval occurrence.

`ctx.tasks.resolveApproval(taskId, decision, note, approvalRequestId)` remains a trusted host integration API. Do not expose it as model-authorized approval or treat model text as the signed owner's decision.

Task approval does not authorize canonical Topic publication, another person's file access, or settlement. Those services retain their own current authority checks.

## Control-plane contracts

The proposed implementation exports version 1 schemas and types from `@ixo/common/work`, and provider interfaces and implementations from `@ixo/oracle-runtime-workers/work`. The Workers root entrypoint also exports the provider APIs. Use a package revision containing these source changes; package publication and deployment remain separate release steps.

| Contract | Binding and behavior |
| --- | --- |
| `SkillManifest` | Binds `skillId`, `skillVersion`, entrypoint `digest`, accepted work types, required `{ with, can }` capabilities, privilege planes, target kinds, timeout, required credential names, output declarations, consequence class, and publisher provenance. |
| `WakeSubscription` | Binds a principal, schedule or Topic source, resource, event filter, cursor, expiry, and `notify` or `evaluate` delivery policy. Its persisted state is `active` or `revoked`. A wake requests evaluation; it grants no authority. |
| `ExecutionTargetProvider` | Prepares a request against a target descriptor, executes or collects a bound receipt, requests cancellation, and releases local resources. Target kind declarations do not establish delivered providers. The branch implements `SandboxExecutionTarget`. |
| `ConsequenceGuard` | Evaluates an `ActionRequest` bound to its principal, resource, input digest, privilege plane, consequence, and evidence or decision references. The decision records the action binding, policy version, reason, and `allow`, `deny`, or `review`. |
| `WorkspaceAdapter` | Binds a workspace to a principal, resource, and root path; snapshots exact artifacts, commits revisions with provenance, restores a pinned revision, and materializes selected bytes into a provider. The branch implements `VfsWorkspaceAdapter`. |

The schemas reject unknown properties. Contract digests are bare lowercase 64-character SHA-256 values. Execution inputs reject reserved configuration keys; callers must still exclude credentials and authorization tokens from ordinary data. Supported target-kind values are `sandbox`, `worker`, `computer`, and `local`; only the sandbox provider is implemented in this research journey.

### Provider and workspace methods

`PreparedExecution` contains the parsed `ExecutionRequest` and `ExecutionTargetDescriptor`. An execution request binds the requester, request ID, work reference, input digest, selected inputs and artifacts, requested capabilities, and timeout. An `ExecutionReceipt` repeats that binding and the provider and target IDs, with timestamps, artifacts, evidence references, and a `completed`, `failed`, `cancelled`, or `unknown` outcome.

| `ExecutionTargetProvider` method | Result |
| --- | --- |
| `materializeArtifacts(files)` | Stages `{ reference: ArtifactRef, bytes: Uint8Array }` inputs. |
| `inspect()` | Returns the target descriptor. |
| `prepare(request)` | Returns the frozen request and target binding. |
| `execute(execution)` | Returns the bound execution receipt. |
| `cancel(execution)` | Returns `requested` or `confirmed`; callers must preserve the distinction. |
| `collect(execution)` | Returns a matching receipt or `null`. |
| `teardown(execution)` | Releases provider resources. |

`WorkspaceAdapter` exposes `open(binding)`, `materialize(target)`, `snapshot()`, `commit(message, provenance)`, `restore(revisionArtifact)`, `listArtifacts()`, and `close()`. Restore takes an `ArtifactRef` for the exact revision file. `VfsWorkspaceAdapter` also exposes `put(name, content, mediaType)` for text artifacts.

An `ArtifactRef` contains `resource`, `fileId`, positive integer `version`, `cid`, `sha256`, `name`, `path`, `mediaType`, and byte count `bytes`. Workspace revisions bind those references, their parent revision, and provenance containing `principalDID`, `workRef`, `inputDigest`, and the commit message. Workspace commit does not publish or accept a Topic.

`VfsWorkspaceAdapter` writes content-addressed objects under `/.workspaces/<workspaceId>/`, verifies returned file versions and digests, and verifies pinned bytes during restore or materialization. Selected materialized files are limited to 10 MiB in total. The research host supplies current-authority callbacks around mutations; VFS independently checks file permissions.

### Guards and durable stores

`ConsequenceGuard.evaluate(action)` is a host policy check. The stock `createConsequenceGuard` returns `allow` or `deny`, rejects the admin plane and settlement, and allows only configured consequence classes after authorization. The research policy permits `none`. A manifest's declared consequence does not enforce filesystem or network restrictions and is not a semantic determination.

`WakeSubscriptionStore` persists subscriptions and deduplicates each subscription/event pair. It checks expiry, revocation, resource, and event type before admitting an operation. Re-registering a subscription cannot silently change its binding or reactivate a revoked subscription. Source adapters must reread current authority; the research Start path separately performs that check.

`ExecutionReceiptStore` persists the prepared binding before execution and checks every receipt against it. A completed receipt can be reused. Finding a started operation without a confirmed completed receipt makes its outcome `unknown` and blocks another target execution. This prevents automatic replay after a lost sandbox response or restart.

## Authorized Topic research API

The proposed implementation adds `TOPIC_RESEARCH_ENABLED=true`, signed owner routes, and the `topic-research-v1` profile. The flag alone is insufficient: the operator must provide `hooks.topicResearch` when constructing the Worker, with a trusted `TopicResearchHost`. Missing host integration fails closed.

| Method | Endpoint | Behavior |
| --- | --- | --- |
| `PUT` | `/topic-research/:operationId` | Start or recover the same frozen research attempt. |
| `GET` | `/topic-research/:operationId` | Read the authenticated owner's persisted snapshot. |
| `POST` | `/topic-research/:operationId/cancel` | Repeat the frozen request, persist cancellation, and abort the task session. |

All three routes require the owner's signed invocation. A reviewer uses their own authority to read the delivered files and review through the canonical Topic repository; they do not receive access to the requester's private operation. Disabled routes return `404`. Research requires a configured `UCAN_STORE_URL`.

### Frozen request and response

Start and cancellation use the same complete body:

```json
{
  "topic": {
    "id": "TOPIC_ID",
    "roomId": "MATRIX_ROOM_ID",
    "threadId": "MATRIX_THREAD_ID",
    "attemptId": "ATTEMPT_ID",
    "observedRevision": "CURRENT_TOPIC_REVISION"
  },
  "title": "Research brief",
  "goal": "Answer the bounded research question",
  "instructions": "Distinguish evidence from inference",
  "sources": [{ "label": "SOURCE_LABEL", "text": "SOURCE_TEXT" }],
  "skill": {
    "id": "PINNED_CAPSULE_CID",
    "version": "PINNED_SKILL_VERSION",
    "digest": "LOWERCASE_SHA256_HEX"
  },
  "capabilities": [{ "with": "RESOURCE", "can": "ACTION" }],
  "credentialNames": ["TOOL_CREDENTIAL_NAME"]
}
```

The placeholder digest must be replaced with 64 lowercase hexadecimal characters; this request also accepts the `sha256:` prefix. The body limit is 1 MiB. The strict schema accepts at most 20 sources, 32 capabilities, and 32 credential names. Title is limited to 160 characters; goal and instructions to 16,000 each; source text to 32,000. IDs, source labels, skill version, and capability values are trimmed nonempty strings of at most 512 characters. Credential names contain letters, digits, and underscores, start with a letter, and allow 128 characters.

`researchInputDigest` hashes the recursively key-sorted JSON of the parsed request, preserving array order and the optional `sha256:` prefix in the requested skill digest. Activation strips that prefix only for pin comparison. The same operation and digest recover existing work; changed inputs return `409` and require a new attempt. Cancellation before Start persists a tombstone that fences a delayed Start. Cancellation after completed execution returns `409`.

Snapshots add `requesterDid`, `inputDigest`, and versioned `artifacts` to the supplied-evidence response fields. Research has the same statuses except `paused`; it cannot become `ready` without committed artifacts. The completed Markdown retains its own SHA-256 digest and timestamp. Matrix delivery and canonical acceptance remain separate from execution completion.

After the completed result is persisted, private requester-notification retries continue independently of current Topic authority. They do not authorize sharing, publication, or review in the canonical Topic repository. Those mutations require current authority and revision checks.

Invalid requests return `400`, unsigned or delegation-only calls `401`, disabled or missing operations `404`, conflicting inputs or late cancellation `409`, oversized bodies `413`, and new work above the per-user limit `429`. Missing host or service configuration is an activation error, not proof of a missing operation.

### Host authority and skill activation

`TopicResearchHost` supplies `allowedSkills`, separate user and oracle credential-name allowlists in `allowedCredentials`, and `resolveTopicAuthority({ principalDid, topic, request })`. The resolver must reread canonical Topic state, room membership, current action authority, and revision after Portal creates the canonical delivery attempt. It returns `{ observedRevision, resourceRef, allowed }` and chooses the VFS resource. Echoing the request's revision does not establish current authority. The runtime compares the resolved revision with the frozen request and rechecks the resource before execution and artifact mutations. The model cannot choose the authority resolver or a replacement storage resource.

Each `ResearchSkillActivation` binds the skill ID, version, entrypoint digest, and declared publisher DID. For this provider the skill ID is its immutable capsule CID. The authenticated registry must contain the selected capsule and a matching JSON `qiforgeManifest` sidecar. The current registry helper requests `skills/*` on `ixo:skills`; the requester's delegation must satisfy that invocation. The manifest is loaded only for the selected research skill; ordinary skill discovery does not activate it.

The host must review and activate a trusted read-only skill with accepted work type `topic-research`, orchestration privilege only, consequence `none`, and sandbox target support. The request must include its required capabilities and credentials, and those credential names must also be host allowed. The provider checks the pinned entrypoint bytes against the manifest digest before running them; the capsule CID pins the bundle. Metadata and matching pins do not independently establish publisher trust or skill safety.

### Execution limits and recovery

The `topic-research-v1` agent binds only the no-argument `run_topic_research` tool. The model receives frozen inputs and committed evidence, then produces Markdown using the operator-selected model. It cannot submit arbitrary code, choose another skill, approve itself, or invoke canonical publication, determination, or settlement tools.

`SandboxExecutionTarget` reports provider `ixo-sandbox`, isolation `principal`, remote locality, and a persistent lifecycle. It uses the existing per-principal sandbox. That sandbox has ambient filesystem and network access; staged input selection does not confine the skill to those inputs or prohibit network writes. Host approval of a pinned trusted skill is the boundary. Do not activate unreviewed skills or describe this target as isolated per execution.

The provider timeout is bounded by the manifest, up to 180 seconds. Cancellation returns `requested`; closing the client does not prove the remote process stopped. Teardown releases local clients and staged input references, and does not wipe the persistent sandbox. Persist required evidence and reports to VFS before target replacement.

The reference path admits an authenticated one-shot Topic research wake through the existing scheduler and run ledger. Recurring research intent and additional wake adapters for webhooks, Model Context Protocol (MCP) events, chain events, voice, and channels remain roadmap work, along with Node runtime parity.

Unknown target outcomes require provider inspection before an explicitly authorized new operation. The ordinary-tool reconciliation routes below do not settle research target receipts. Reusing a completed receipt and retrying delivery must not run the skill again.

## Unknown-write reconciliation

An interrupted external write stays blocked across later turns and run-history retention. Warning the model or restarting the Worker does not establish whether the effect occurred.

The implementation exposes owner-invocation-only routes:

| Method | Endpoint | Behavior |
| --- | --- | --- |
| `GET` | `/write-reconciliations` | List outstanding write claims for the authenticated owner. |
| `POST` | `/write-reconciliations/:fingerprint` | Record an outcome and explicit retry authorization for the original run. |

`fingerprint` is a lowercase 64-character hexadecimal digest. Reconciliation requires:

```json
{
  "expectedRunId": "ORIGINAL_RUN_ID",
  "evidenceRef": "PROVIDER_RECONCILIATION_RECORD",
  "outcome": "not-applied",
  "authorizeRetry": true
}
```

`outcome` is `applied`, `not-applied`, or `unknown`. `authorizeRetry: true` is valid only with `not-applied`. A successful response is `{ "resolved": true }`; stale run binding or conflicting evidence returns `409`, and an invalid body returns `400`.

The owner provides the evidence reference and outcome. Recording that reference does not independently verify an external provider's state. Confirm the effect with the provider before authorizing a retry. An `applied` or `unknown` record does not release the claim for automatic replay.

In the proposed implementation, ordinary Composio tools permit only `COMPOSIO_SEARCH_TOOLS` and `COMPOSIO_GET_TOOL_SCHEMAS`. Consequential or unknown execution, including multi-execute and connection-management calls, is blocked before its SDK tool invocation because the installed SDK can retry effects internally. These remaining tools discover names and schemas; they do not execute a discovered research or application action. There is no activation flag or available verified no-retry transport for consequential Composio execution.

## Sandbox credential selection

Workers sandbox discovery forwards no user or operator tool secrets. Execution forwards only host-selected names through `SandboxPlugin({ selectCredentials })`, or through the configured comma-separated `SANDBOX_USER_SECRET_NAMES` and `SANDBOX_ORACLE_SECRET_NAMES` allowlists. With no selection, neither category is forwarded.

`ORACLE_SECRETS` supplies available operator tool secret values; it does not select every value for forwarding. Selected user secrets use the existing filtered secret adapter, which excludes runtime-only model credentials and OAuth tokens. Deployments that depended on implicit forwarding must configure the required names.

Credential names are execution inputs; values remain inside the host-to-target credential channel. They must not enter skill manifests, work definitions, workspace revisions, artifact receipts, or review records. A named credential never grants the associated UCAN capability.

For the research provider, forwarded names must be required by the manifest, selected in the frozen request, and allowed by the host for the appropriate credential category. Runtime-only model credentials remain excluded. Exact selected raw values are scrubbed locally from target results and failures before use by the model, VFS, or receipts, including values shorter than eight characters. This supplements the upstream sandbox scrub, whose minimum length is eight characters.

Local scrubbing does not change upstream sandbox logs or guarantee removal of encoded or transformed secrets. Operators must review upstream logging and retention before activation. The sandbox still receives the selected values; host selection and output scrubbing do not establish end-to-end confidentiality.
